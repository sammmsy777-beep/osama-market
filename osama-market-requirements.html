1. Project Overview

1.1 Description

"Osama Market" is an integrated management system for a market/retail store, combining:

  • A Cashier (Point of Sale) system for daily sales transactions.
  • A financial & analytics management system covering purchases, sales, debts, and inventory.
  • A simple, fast user interface, designed with a visual language inspired by Apple's Human Interface Guidelines: large clear icons, comfortable white space, and smooth transitions.

Important note: although this document and the source code comments/labels are written in English, the application's user-facing interface must remain fully in Arabic (all on-screen text, labels, buttons, and messages shown to the end user are Arabic, using the Readex Pro font). English here refers only to the documentation and internal code identifiers.

1.2 Goals

  1. Make daily store management easy without requiring technical expertise.
  2. Provide a clear financial picture (profit/loss, debts, inventory) at any moment.
  3. Work fully offline (offline-first) via a local database.
  4. Be extensible later (desktop + Android apps) from the same codebase.

2. Target Users

  • The market owner and staff (cashier, inventory manager).
  • Users who may not have high technical expertise → priority on simplicity and clear icons.

3. Design Requirements (UI/UX)

3.1 Visual Identity

  • Color palette:
    • Primary: turquoise (suggested: #1ABC9C, with a lighter shade #5FD3C4 for interactions, and a darker shade #128C7E for text/borders).
    • Secondary: white #FFFFFF and very light gray backgrounds #F5F7F7 to reduce eye strain.
    • Semantic colors: green for success/profit, light red for debts/alerts, orange for warnings — kept within the same calm visual tone (not overly saturated).
  • Font: Readex Pro from Google Fonts (full Arabic support, weights 160–700) — used across the entire interface for text and numbers.
  • Icons: large and clear, simple line/outline or soft-flat style, uniform sizing, resembling iOS icons in roundness and simplicity.
  • Corners & shadows: soft rounded corners (relatively large border-radius), very light shadows for subtle depth without visual clutter.

3.2 User Experience

  • Responsive design that works equally well on desktop and mobile screens.
  • Full RTL (right-to-left) support since the interface is entirely in Arabic.
  • Smooth transitions/animations between screens (light fade/slide), short duration (200–300ms) so it never feels slow.
  • A home dashboard showing a quick summary: daily sales, profit, outstanding debts, inventory status.
  • Primary navigation via a side or bottom menu with large icons for each main section.
  • Support for both Light and Dark mode — optional (nice to have), not required in Phase 1.

3.3 Main Interface Sections

  1. Home / Dashboard
  2. Cashier (Point of Sale)
  3. Purchases
  4. Sales
  5. Debts (owed to the store / owed by the store)
  6. Inventory
  7. Reports & Analytics
  8. Settings

4. Detailed Functional Requirements

4.1 Cashier (POS) System

  • Fast sale screen: search for a product (by name or barcode), add to cart, edit quantity, remove an item.
  • Automatic total calculation (with optional manual discount).
  • Payment methods: cash / debt (deferred) — automatically logged in the Debts section when "debt" is selected.
  • Completing a sale → automatically updates inventory (deducts sold quantity).
  • Display/print a simplified invoice for the transaction (later: actual printing or PDF support).
  • Keyboard shortcuts for frequent operations (to speed up cashier work).

    • 4.1.1 Sale Return / Void Sale NEW

    The cashier system must support reversing a completed sale, covering two distinct cases:

    • Void (cancel) a sale: cancels a sale made within the same active session, before the cashier moves to another transaction — typically used to correct an immediate mistake. Fully removes the transaction as if it never happened.
    • Return (refund) a sale: reverses a sale that was already completed and closed (possibly on a previous day), whether as a full return or a partial return of specific items from the original invoice.

    Functional rules:

    • Every return/void must reference an original sale record (searchable by invoice number, date, or customer).
    • Inventory must be automatically restored (quantity added back) for every returned/voided item.
    • If the original sale was paid in cash, the refunded amount is recorded as a cash outflow; if it was on debt, the corresponding debt balance must be reduced accordingly.
    • Partial returns must recalculate the remaining invoice total and update the sales record without deleting the original invoice history.
    • Every return/void operation must be logged in the audit log (see Section 6) with: user who performed it, date/time, reason (optional text field), and the affected items/amount.
    • A return/void action requires an explicit confirmation step (cannot be triggered accidentally).
    • Permission restriction: depending on the role system (Section 6), voiding/returning a sale may require owner approval or a specific permission, since it directly affects inventory and cash records — this should be configurable in Settings (e.g., "cashier can void within X minutes of sale" vs "returns always require owner login").
    • The dashboard and reports must reflect returns/voids correctly (i.e., net sales = gross sales − returns), not just raw totals.

4.2 Purchases

  • Record new purchase invoices (supplier, products, quantities, purchase price, date).
  • Automatic inventory link (quantity increases when a purchase invoice is recorded).
  • Full purchase history view with filtering (by date / by supplier).

4.3 Sales

  • Full record of all sales generated from the cashier, including returned/voided ones (clearly marked).
  • Filtering by date (daily/weekly/monthly), by product, or by payment method.
  • Display of net sales and estimated profit (sell price − purchase price) per period, after accounting for returns.

4.4 Debts

  • Debts owed by the store (to suppliers): resulting from purchases on credit.
  • Debts owed to the store (by customers): resulting from sales on credit via the cashier.
  • Manual entry of a new debt (party name, amount, date, note).
  • Recording partial/full repayments, automatically updating the remaining balance.
  • Debt balances must automatically adjust when a related sale is returned or voided (see 4.1.1).
  • Visual alert (red/orange) for overdue or high-value debts.

4.5 Inventory

  • Full product list: name, category, current quantity, purchase price, sell price, low-stock threshold.
  • Automatic alert when a product approaches out-of-stock (Low Stock Alert).
  • Add/edit/delete a product, with barcode support (optional in Phase 1, standard later).
  • Product categorization into sections for easier browsing/search.
  • Inventory quantities automatically restored when a sale is returned/voided.

4.6 Reports & Analytics (Budget Dashboard)

  • Comprehensive financial summary: total sales (net of returns), total purchases, net profit, total debts (owed to/by), current inventory value.
  • Simple charts for sales/profit over time (daily, weekly, monthly).
  • A dedicated view/filter for returns and voided sales, to track their frequency and value.
  • Report export (PDF or Excel) — required in a later phase, after the database is connected.

4.7 Settings

  • Store information (name, logo, currency used).
  • User/permission management (owner, cashier), including the return/void permission rule from 4.1.1.
  • Local database backup and restore.
  • Language switch (Arabic is the default and required app language; English optional later — see note in Section 1.1).

5. Technical Architecture & Tools

5.1 Phase 1 — Prototype (Frontend Only)

  • Single file only: index.html containing HTML + CSS + JavaScript (no separate files at this stage, per client request).
  • Font: load Readex Pro from Google Fonts via <link> or @import.
  • Mock data stored in JavaScript variables to simulate all screens and features, including sample voided/returned sale records to demo the new feature.
  • Responsive design using CSS (Flexbox/Grid) without any heavy external framework at this stage.

5.2 Phase 2 — Local Database (Realm)

  • Use Realm Database (Realm JS SDK) for persistent local storage.
  • Data schema design for each core entity:
    • Product: id, name, category, purchasePrice, sellPrice, quantity, minQuantityAlert, barcode
    • Sale: id, date, items[], total, paymentType (cash/debt), customerId?, status (completed/voided/returned), returnedItems[]
    • Purchase: id, date, supplierName, items[], total
    • Debt: id, type (customer/supplier), partyName, amount, remainingAmount, date, status
    • User: id, username, passwordHash, role (owner/cashier)
    • AuditLog: id, userId, action (sale/void/return/delete/...), timestamp, details
    • StoreSettings: storeName, currency, logo
  • All operations (sale, purchase, debt repayment, return/void) must update related entities within a single transaction to guarantee data consistency (e.g., a sale return restores inventory, adjusts the sale record, and adjusts the debt balance in one atomic operation).

5.3 Phase 3 — Desktop App (Electron)

  • Package the interface using Electron to produce a Windows/macOS/Linux app.
  • Realm runs natively (native Node module) directly inside the Electron environment.
  • Support automatic app updates later (optional — Electron Auto Updater).
  • Generate installers via a tool such as electron-builder.

5.4 Phase 4 (Future) — Android Version

  • Use Capacitor to package the same HTML/CSS/JS interface as a real Android app (not just a web page inside a permission-less WebView).
  • Use the Realm package compatible with React Native/Capacitor to keep the same data schema, with a sync or export/import mechanism between the desktop and Android versions if unified data across devices is required later.

6. Security Requirements

Since the app manages sensitive financial data, security is mandatory, not optional:

  1. Mandatory login with a password, using password hashing (e.g., bcrypt) — never stored as plain text.
  2. Role-based permissions:
    • Owner: full access to all sections, reports, and settings, including approving returns/voids when required.
    • Cashier: access limited to the cashier screen and possibly inventory (view-only), without access to full financial reports or settings. Return/void access is governed by the configurable rule from Section 4.1.1.
  3. Local database encryption (Realm supports built-in AES-256 encryption) to protect the local file if the device is lost or stolen.
  4. Periodic backup (automatic or manual) of the database with restore capability.
  5. Audit log recording who performed any sensitive operation (sale, delete product, edit debt, void/return sale) and when — to prevent internal manipulation.
  6. Protection against accidental deletion: any delete operation (product, invoice, debt) requires explicit user confirmation, and the same applies to sale return/void actions.

8. Acceptance Criteria — Phase 1

  • ✅ A single HTML file that runs directly by opening it in any modern browser, with no extra setup.
  • ✅ All eight sections (Section 3.3) exist and are navigable with smooth transitions.
  • ✅ Readex Pro is used across all text.
  • ✅ Colors match the defined visual identity (turquoise/white/teal).
  • ✅ The design is responsive (works equally well on desktop and mobile screen sizes).
  • ✅ A complete sale flow from the cashier (select product → cart → complete sale) is testable with mock data.
  • ✅ A complete sale return/void flow is testable with mock data: selecting a past sale, returning/voiding it (fully or partially), and seeing inventory, sales totals, and debt balances update accordingly.
  • ✅ A main dashboard displays (mock, at this stage) figures for: sales, profit, debts, inventory.
  • ✅ All user-facing text in the running app is in Arabic, despite this specification and code comments being in English.

9. Risks & Notes

Moving from a "single file" to a multi-file structure: when reaching Phase 2 (Realm), it is not practically possible to remain in a single HTML file, since Realm requires a Node.js/Electron environment. At that point, an organized project structure will be agreed upon (folders: main, renderer, database, assets), while fully preserving the same design and visual identity.
Security vs. simplicity: the "easy and simple" feature must not weaken security requirements (login, permissions) — especially for sensitive actions like sale returns/voids. A simple but secure login flow will be designed (e.g., a large-icon login screen with a numeric PIN for the cashier, and a full password for the owner), with the return/void permission rule enforced regardless of how simple the login feels.
Android via Electron is not technically possible — the alternative (Capacitor) is outlined in Section 5.4, and this choice should be confirmed with the client before reaching that phase.
